# Аудит пяти сторонних модов нестандартных контрактов

**Дата:** 2026-10-23 · **Статус:** изучены исходники всех пяти пользовательских архивов, это не проверка их работы в игре.  
**Назначение:** приложение к [TECHNICAL_DESIGN.md](TECHNICAL_DESIGN.md) и [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md).  
**Источники:** пользовательские архивы `FS25_Longtermcontracts.zip`, `FS25_RollerMission.zip`, `FS25_LimeMission.zip`, `FS25_Pallet_delivery_contracts.zip`, `FS25_SupplyTransportContracts.zip`. Файлы из архивов не добавлены в репозиторий, используется только анализ.

## 1. SupplyTransportContracts — главный образец поставок

- `scripts/main.lua:129`: регистрация `SupplyTransportMission` через `g_missionManager:registerMissionType`.
- `scripts/missions/SupplyTransportMission.lua` (1058 строк): наследование `AbstractMission`, собственные поля объёма, цены и пункта продажи; сериализация XML (`saveToXMLFile` ~241, `loadFromXMLFile` ~273), потоки клиента (`writeStream` ~167, `readStream` ~185).
- `tryGenerateMission` (~886): фабрика контракта; текущая реализация выбирает товары/точки по своим правилам, **не по нашим требованиям** одного задания в месяц.
- `fillSold` (~549): увеличивает `depositedLiters` и при достижении порога убирает миссию из `sellingStation.missions`. Это пример штатной сцепки со `SellingStation:addFillLevelFromTool`.
- `finish` (~501): снимает регистрацию станции и hotspot, вызывает базовое завершение. При неуспехе рассчитывает компенсацию за уже доставленную продукцию. **Эту экономику нельзя переносить автоматически**: наши выплаты пока требуют отдельного решения.
- `SupplyTransportManager.lua` имеет механизм удаления/перегенерации предложений через `markMissionForDeletion`, `updateMissions`, `tryGenerateMission` (~186–228). В нашей системе использовать генерацию по игровому месяцу, не копировать произвольное обновление списка.
- Полезно: восстановление ссылки на станцию, проверка исчезнувшей точки, hotpot, сеть, сохранение, генератор.

## 2. Pallet_delivery_contracts — приёмка поддонов, блокировка обычной оплаты

- `scripts/contract/PalletDeliveryMissionReg.lua:8–15`: регистрация нового типа миссий.
- `PalletDeliveryMission.lua` (1214 строк), `fillSold` (~774): отдельный накопитель объёма и `raiseDirtyFlags`; `matchesStationDelivery` (~787) соотносит станцию, товар и ферму.
- `finish` (~745) и `dismiss` (~766) очищают созданные поддоны, hotspots и затем вызывают базовый lifecycle.
- В районе строк 1100–1145 имеются обёртки денежных начислений и `UnloadTrigger.addFillUnitFillLevel`: до штатного вызова определяется контрактная поставка, после него используется **реально принятый** объём; временный маркер `_suppressMoneyForFarmId` подавляет обычную оплату в соответствующем проходе.
- В районе 1149 и далее есть отдельная обработка `PalletUnloadTrigger.unloadPallets`; такой код очень инвазивен. **Не копировать хуки целиком**; проверить для скупщика карты путь выгрузки, возможные побочные эффекты для других модов и совместимость с версией FS25.
- Полезно как подтверждение, что путь приёмки поддонов может отличаться от обычной станции, и как пример отслеживания реального объёма.

## 3. Longtermcontracts — длительные контракты и месячные периоды

- `ProductionContract.lua` (1107 строк) наследуется от `AbstractMission`; `tryGenerateMission` (~317) проверяет сервер, существующие предложения и лимит экземпляров.
- В `scripts/main.lua:62–84` перехватывается `UnloadingStation.addFillLevelFromTool` через `Utils.overwrittenFunction`, после базового вызова подсчитываются **реально принятые** литры. Приёмка продукции производством не вызывает `fillSold` автоматически.
- `ProductionContract:fillSold` (~536) различает разовую и годовую поставку; для длинного контракта объём считается в текущем периоде.
- `ProductionContract:finish` (~676) отписывается от `MessageType.PERIOD_CHANGED`, удаляет привязку к станции и проводит расчёты годового задания.
- Полезно для календарной генерации, контроля длительных заданий, восстановления/очистки ссылок.
- **Не копировать** периодические выплаты, поскольку по ТЗ нужна единичная ежемесячная генерация предложений для одной из трёх точек, а не годовые поставки.

## 4. LimeMission и RollerMission — малые образцы регистрации полевых миссий

- `limeMission.lua` (180 строк), `RollerMission.lua` (155 строк) добавляют виды работ, регистрируют их через `g_missionManager:registerMissionType`, используют `tryGenerateMission` и специализированные проверки полей.
- Подходят как краткий образец наследования существующей полевой миссии и регистрации XML параметров, но **не годятся как основа лесных миссий**: у нас отдельные непокупаемые `farmland`, права на деревья/пни и нет стандартной обработки поля.

## 5. Сопоставление с текущими исходниками FS25 и картой

Подтверждено чтением `scripts/objects/SellingStation.lua` в репозитории игры: `addFillLevelFromTool` ищет подходящую миссию в `self.missions` и вызывает `fillSold(deltaFillLevel)`; `sellFillType` зачисляет деньги. Это обосновывает изучение пути станций и денежной схемы, но ещё **не доказывает**, что все три точки карты используют одинаковый обработчик.

В текущем `map/map.xml` карты перечислены штатные классы с XML-именами: `deadwoodMission`, `treeTransportMission`, `destructibleRockMission`. Именно эти типы надо искать в регистрации игры для правил +1/−2; названия нельзя путать с предложениями `TransportMission`/камнями из других версий.

В `config/farmlands.xml` есть `farmland id="100" priceScale="0" npcName="FORESTER" showOnFarmlandsScreen="false"` — реальный пример скрытия существующего участка. **Не утверждать**, что это уже полностью запрещает приобретение через все механизмы: требуется аудит `FarmlandManager` и интерфейса покупки.

В карте уже работает `LoggingContractor:scanFarmlandTrees` (`scripts/loggingContractor/LoggingContractor.lua:186`): сканер на `overlapBox` отбирает стоящие STATIC MESH_SPLIT_SHAPE, исключает пни и срубленные части, подтверждает принадлежность через `getFarmlandIdAtWorldPosition`, группирует породы. Для нашей инвентаризации полезно **повторно использовать критерии**, но текущий метод проверяет принадлежность участка ферме и не возвращает идентичности всех деревьев или M литров. Его нельзя прямо использовать без адаптации.

В `scripts/constructionLifecycle/ConstructionLifecycleFix.lua:834+` имеется отслеживание переходов `spec_constructible` между состояниями и фильтр корректного продвижения `stateTransitions`; уведомления не отправляются при первой загрузке. Для контрактного завершения потребуются серверная проверка и надёжное сохранение, а не подписка на клиентский HUD.

## 6. Рекомендации архитектуры и задачи для следующего прохода

1. В качестве основного образца новой миссии разобрать `SupplyTransportMission`; выбирать события и API только после сравнения со штатной FS25 1.25.0.0.
2. Для паллет исследовать `PalletUnloadTrigger` отдельно; не переносить глобальное подавление денег без строгого скоупа по ферме, точке и товару.
3. Для месячной генерации использовать отдельный сохранённый идентификатор периода, а не полагаться на частоту штатного `tryGenerateMission`.
4. Для лесных участков использовать подтверждённую проверку координат по `farmlandId`, отдельно проверить права на рубку и корчевание и сериализацию ID деревьев.
5. Сопоставить `deadwoodMission`, `treeTransportMission`, `destructibleRockMission` с кодом регистрации/завершения и проверить точные методы.
6. Найти реальные три точки продажи на карте, типы триггеров и трассы обработки товаров; затем принять решение по блокировке обычной продажи.
7. Проверить параметры `farmland`, рост дерева, перерасчёт N/M и взаимодействие с существующим лесным подрядчиком.
8. Не отмечать этап 1 плана завершённым до полного проверки перечисленных механизмов.
